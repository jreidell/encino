# encino on-disk format, version 1

Normative description of what encino writes to disk. Anything not specified here
is an implementation detail and may change without a version bump.

For what encino is and how to use it, start at the [README](../README.md).

All multi-byte integers are little-endian. All binary values embedded in JSON are
base64 (standard alphabet, padded).

## Directory layout

```
<vault folder>\
  .encino\
    vault.json            format version, KDF parameters, wrapped keys
    index.enc             AEAD-sealed document index
    index.enc.bak         previous generation of the index
    blobs\
      0f\
        0f3a91c7…          one encrypted document
    journal\
      <op-id>.json        in-flight operation records
    staging\
      <op-id>             plaintext being assembled by a checkout (see below)
    work.lock             held open for the life of a session (see below)
  <checked-out documents appear here as plaintext>
```

The vault folder's root is the plaintext work area. When no document is checked
out it contains nothing but `.encino`. This is deliberate: anything visible in
the root is, by definition, currently decrypted.

## vault.json

Plaintext, and intentionally so. It holds only KDF parameters, salts, and wrapped
key blobs, none of which are secret; keeping it readable means a vault can be
inspected without the passphrase — which algorithm protects it, at what cost,
and how many credentials can open it.

```jsonc
{
  "format_version": 1,
  "vault_id": "9f1c…",           // UUIDv4, identifies this vault
  "created": "2026-08-01T12:00:00Z",
  "kdf": {
    "algorithm": "argon2id",
    "version": 19,                // Argon2 version 0x13
    "memory_kib": 65536,
    "iterations": 3,
    "parallelism": 1
  },
  "wraps": [
    { "kind": "passphrase", "salt": "…", "nonce": "…", "ciphertext": "…" },
    { "kind": "recovery",   "salt": "…", "nonce": "…", "ciphertext": "…" }
  ]
}
```

`kdf` parameters are calibrated at `init` to roughly one second on the machine
that created the vault, floored at the OWASP minimum of 19 MiB and two
iterations. They are stored rather than hardcoded because the cost that opens a
vault must be the cost that created it — a binary carrying a different hardcoded
figure would derive a different key and open nothing. Recording them makes the
cost a property of the vault rather than of the build, which is what allows the
defaults to be raised at all.

Each entry in `wraps` is an independent encryption of the same 32-byte master
key. Each carries its own 16-byte salt and 24-byte nonce. `kind` is a hint for
error messages only — unwrapping is attempted against the supplied credential and
its result is authenticated, so a mislabelled entry cannot be exploited.

Wrap associated data binds the wrap to its vault, so a wrap cannot be transplanted
between vaults:

```
AAD = "encino:wrap:v1" ‖ vault_id (16 bytes)
```

## Key hierarchy

```
passphrase ──Argon2id(salt_p)──► KEK_p ──┐
                                          ├──► master key (32 random bytes)
recovery code ──Argon2id(salt_r)──► KEK_r ┘         │
                                                    ├─HKDF-SHA256 "encino:index:v1"──► index key
                                                    └─HKDF-SHA256 "encino:blobkey:v1"──► blob-key-wrapping key
```

The master key is generated by the OS CSPRNG and never derived from the
passphrase. This is what makes `passwd` cheap: rotating a passphrase rewraps the
master key and rewrites `vault.json`, touching no document.

HKDF context strings are distinct per purpose so that no two roles ever share key
material.

Each document additionally has its own random 32-byte content key, stored wrapped
under the blob-key-wrapping key inside the index. Per-document keys mean that
rekeying or destroying one document never disturbs another.

## Blobs

One file per document, at `.encino\blobs\<first byte in hex>\<blob id in hex>`.

**Blob IDs are 16 random bytes, not a hash of the content.** Content addressing
would give identical documents identical names, which leaks the fact that two
documents are the same and lets an attacker confirm a guessed document's presence
by hashing a candidate and looking for the name.

The single-byte shard prefix exists to keep directory sizes reasonable; it is not
a security property.

### Blob encoding

```
magic         8 bytes    "ENCINOB1"
chunk_size    4 bytes    plaintext bytes per chunk (1 048 576 in v1)
chunk_count   8 bytes    number of chunks that follow
plaintext_len 8 bytes    the document's true length, before padding
chunks        chunk_count × (24-byte nonce ‖ ciphertext ‖ 16-byte tag)
```

Every chunk is sealed with XChaCha20-Poly1305 under the document's content key
with a fresh random nonce. Chunking bounds memory: a multi-gigabyte document must
not require full materialization in RAM to be verified.

The chunks cover `padded_len(plaintext_len)` bytes of plaintext: the document
followed by zeros. A reader emits only the first `plaintext_len` of them.

### Size padding

```
MIN_BLOB_BYTES = 4096

padded_len(L):
    if L ≤ MIN_BLOB_BYTES: return MIN_BLOB_BYTES
    E = ⌊log₂ L⌋
    S = ⌊log₂ E⌋ + 1
    return L rounded up to a multiple of 2^(E−S)
```

This is Padmé, from the PURB paper, with a floor. Without padding a blob's size
approximates its document's, which is enough to confirm a guessed document —
a specific tax form, a specific contract — without any ability to decrypt it.

Padmé bounds the *relative* leak: overhead is at most 11.9%, and what a file's
size still reveals is roughly `log log L` bits. The floor supplies what Padmé
alone does not, which is that every document below 4 KiB is exactly the same size
on disk; Padmé pads a 200-byte note to 200 bytes and leaves it as identifying as
it was.

Padding is zero-filled and lies inside the AEAD, so it is indistinguishable from
content. A reader must reject padding that is not zero. That check stops no
attack — sealed padding cannot be forged — but it makes the rule normative, so a
divergent implementation fails loudly instead of quietly.

`padded_len` is monotonic, which matters: a bucket function that let a larger
document produce a smaller file would leak more than the padding hides.

Readers must reject a `plaintext_len` above 2⁴⁸, which bounds the arithmetic
above against a hostile header.

### Chunk associated data

Each chunk's associated data binds it to its document, its position, whether it
ends the document, and — on the final chunk — the document's true length:

```
AAD = "ENCINOB1" ‖ blob_id (16) ‖ chunk_index (8) ‖ is_final (1) ‖ len_field (8)

len_field = plaintext_len   on the final chunk
          = 0               on every other chunk
```

Binding the blob ID defeats splicing chunks between documents; binding the index
defeats reordering; binding `is_final` defeats truncation; binding
`plaintext_len` defeats a re-declared length.

That last one is what padding makes necessary. `plaintext_len` sits in the
unauthenticated header, and with slack after the document an attacker who could
re-declare the length would truncate the plaintext while every chunk still
verified — the reader would simply treat the rest as padding. Binding it closes
that, and no other chunk can be promoted to final because `is_final` is bound too.

**Why only the final chunk carries it.** The true length is unknown until the
source is exhausted. Binding it into every chunk would mean no chunk could be
sealed until the whole document had been read, which forfeits streaming. The
final chunk is the one place a streaming writer already knows the total, and one
authenticated binding is all it takes to make the header field unforgeable. This
is the same trade as `is_final` standing in for `chunk_count` below.

That last one carries the subtlety. The header is not authenticated, so an
attacker can freely edit `chunk_count`. Dropping the last chunk *and* decrementing
the count would leave every surviving chunk verifying correctly under its own key
and position — silent truncation. With `is_final` bound in, the new last chunk was
sealed as non-final and fails to open. Appending a chunk fails for the mirror
reason.

Binding `chunk_count` itself would be the more obvious choice, but the count is
unknown until the input is exhausted, and a streaming writer must seal each chunk
as it goes. The flag carries the part that matters and needs only one chunk of
lookahead.

**Every blob has at least one chunk.** A zero-length document is stored as a
single final chunk of 4096 padding bytes, not as zero chunks. Otherwise a blob
truncated to its header alone would be indistinguishable from a legitimately
empty document. A reader must reject `chunk_count == 0`.

All chunks are full except the last, which may be shorter.

A reader must also check that the chunks decrypt to exactly
`padded_len(plaintext_len)` bytes. The padded length is *derived* from the
authenticated length and never read from the file: a padding length the file
could choose is a padding length an attacker chooses.

### Timestamps

Every blob, every shard directory, and `blobs/` itself carries a fixed
modification and access time of `2001-01-01T00:00:00Z`.

A blob is written once and never modified — an edited document is stored under a
fresh random id — so without this a blob's mtime is exactly when that document
last changed, and a shard's mtime is when one of its documents last changed.
Across the snapshots a backup accumulates, that is a per-document activity
timeline available without any credential.

This is a property of what encino writes rather than of the format: a version 1
reader never consults a timestamp.

Setting it is best-effort, since a filesystem that refuses must not fail an
import. That makes it the one property here that can be absent without anything
going wrong at the time, so `encino verify` reports any blob left carrying a
real timestamp.

**On Unix, ctime is not covered**, because no userspace call can set it — and
setting mtime updates it. An attacker reading the raw filesystem still sees when
each blob was written. What this does cover is every backup and archive format,
none of which carry ctime, which is precisely the case where a timeline
accumulates over repeated copies.

A shard directory emptied by a deletion is removed rather than left standing.
An empty shard records that a document once lived there, which outlives the
document and accumulates as edits replace blobs, so the store would gradually
disclose more than it holds. Shards are recreated on demand, so a reader must
not assume any particular shard exists.

`index.enc` and `vault.json` are deliberately excluded. They are replaced in
place, keeping their names and sometimes their sizes, so a tool deciding what to
copy from name, size and mtime could silently skip a changed index — and the
index is the one file whose loss loses every document.

## index.enc

A single AEAD-sealed JSON document. Because logical paths exist only here, both
filenames and the directory tree are hidden; the blob store is flat and reveals
no structure.

```
magic       8 bytes    "ENCINOI1"
nonce      24 bytes
ciphertext  …          XChaCha20-Poly1305 under the index key, AAD = magic ‖ vault_id
tag        16 bytes
```

Plaintext:

```jsonc
{
  "documents": [
    {
      "path": "taxes/2024-w2.pdf",     // logical path, always forward slashes
      "blob_id": "0f3a91c7…",
      "wrapped_key": { "nonce": "…", "ciphertext": "…" },
      "size": 1258291,                  // plaintext bytes
      "sha256": "…",                    // of the plaintext, for `verify`
      "modified": "2026-04-11T09:31:02Z",
      "added": "2026-08-01T12:04:55Z"
    }
  ]
}
```

Index associated data is `"ENCINOI1" ‖ vault_id`, which prevents an index from one
vault being substituted into another.

`modified` and `added` are RFC 3339. The example above is rounded for legibility;
real values carry whatever sub-second precision the source timestamp had, as in
`2026-08-07T08:33:20.551008Z`. A reader must accept a fractional part, and a
writer may emit one. `encino ls --json` reports both fields in the same form.

Each `wrapped_key` is the document's content key sealed under the
blob-key-wrapping key, with associated data binding it to the blob it decrypts:

```
AAD = "encino:contentkey:v1" ‖ blob_id (16 bytes)
```

Without that binding, repointing an index entry at a different blob would let one
document's key be applied to another's ciphertext.

### Atomic replacement

The index is the single point of total failure: lose it and every blob becomes
unrecoverable noise. It is therefore replaced by write-temp, fsync, rename,
fsync-the-directory, and the prior generation is retained as `index.enc.bak`.
`rename` over an existing file is atomic on NTFS, so a crash leaves either the
old index or the new one.

The second fsync is what makes the *name* durable and not merely the bytes.
Without it a power failure can leave a fully flushed file that no directory entry
points at, which recovery reads as an operation that never completed — and by
then `add` has already shredded the original. It is best-effort, because there is
no portable directory fsync: Windows has no handle to open this way, and some
network filesystems refuse. Blobs get the same treatment on their shard.

Only a primary that still decrypts is copied to `index.enc.bak`. A damaged
primary is exactly when the backup is about to be the only surviving copy, so
that is the one moment it must not be overwritten with the damage. When the
backup is used, the session says so: it is a generation old, so any document
added since is no longer indexed and its blob is left orphaned, which `verify`
reports.

## Journal

One JSON file per in-flight mutation, named for its operation ID, written before
the mutation begins and deleted after it completes. A non-empty journal at
startup means a previous run was interrupted, and triggers roll-forward or
rollback.

```jsonc
{
  "op_id": "…",
  "kind": "checkout" | "checkin" | "add" | "remove",
  "path": "taxes/2024-w2.pdf",
  "blob_id": "0f3a91c7…",
  "stage": "started" | "data-written" | "index-updated"
}
```

The invariant that must never break: **a document is only removed from its old
state once its new state is durable.** Checkout fsyncs the plaintext before
clearing the journal entry; check-in fsyncs the new blob before shredding the
plaintext.

## staging

Scratch space for a checkout in progress. A document is decrypted to
`staging\<op-id>`, checked against the size and digest recorded in the index,
and only then renamed into the work area. A failure anywhere in that sequence
leaves a partial file here rather than one in the work area that looks whole,
and the partial is shredded rather than unlinked, since it holds plaintext.

Staging sits inside `.encino` so that it shares a volume with its destination,
which is what makes the final move an atomic rename rather than a copy.

Two further transient names appear and disappear inside `.encino`: files
matching `.<name>.<random>.tmp` are the write-then-rename siblings used to
replace `vault.json`, `index.enc`, and journal records atomically. Neither these
nor staging files are left behind deliberately; anything found in either place
is debris from an interrupted run.

## work.lock

Grants one session exclusive access to a vault, held open for the session's
lifetime. On Windows it is opened for writing while denying write sharing; on
Unix it carries a non-blocking exclusive `flock`.

**The lock is the open handle, not the file.** A `work.lock` left on disk by a
process that died grants nothing and is simply reused by the next session. The
operating system releases the handle when the holder exits for any reason, so
there are no stale locks, no timeout to tune, and no override flag. Read sharing
is permitted so that a refused process can read the holder record and say who is
in the way:

```jsonc
{ "machine": "DESKTOP-ABC", "pid": 8412, "since": "2026-08-02T09:31:02Z" }
```

The contents are a courtesy for the error message and carry no authority; only
the handle does.

Both platforms rely on the same property: the lock belongs to the open handle,
not the file, so the kernel releases it however the process dies.

Over SMB the server enforces the same share mode across clients, which is what
makes this work for vaults on a network share. See
[threat-model.md](threat-model.md) for why merging concurrent writers is not an
option: index entries carry per-document content keys, so a lost update destroys
a document rather than merely reordering history.

A session takes the lock *before* reading the index. Reading first would leave a
window in which another session could replace the index in between.

## Reserved for future versions

Changes requiring a `format_version` bump:

- **Hiding the document count.** Padding hides how large each document is, but
  the number of blobs is still a directory listing away. Closing that needs
  decoy blobs, whose cost is ongoing rather than one-off.
- **Additional key wraps.** The `wraps` array is already a list, so adding a
  TPM- or Windows-Hello-sealed entry is additive and may not need a bump.
- **Compression** before encryption. Not in v1: compressing before encrypting
  leaks information through ciphertext length, and the documents this tool
  targets are mostly already-compressed PDFs and images.
